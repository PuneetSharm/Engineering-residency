# Learning Rules

> **"Good engineers don't just learn more—they learn better."**

---

# Why These Rules Exist

Programming languages, frameworks, libraries, and AI tools will continue to evolve throughout your career.

Learning how to learn is a skill that lasts much longer than learning any specific technology.

The rules in this document define the learning philosophy for this Engineering Residency.

These rules apply to every chapter, every assignment, every project, and every discussion throughout this handbook.

Whenever you feel lost or unsure how to approach a topic, return to this document.

---

# Rule 1 — Understand Before You Memorize

Never memorize syntax before understanding the problem it solves.

If you know **why** something exists, remembering **how** to use it becomes much easier.

---

# Rule 2 — Always Ask "Why?"

For every new concept, answer these questions:

- Why does it exist?
- What problem does it solve?
- What would happen if it didn't exist?
- When should I use it?
- When should I avoid it?

If you cannot answer these questions, your understanding is incomplete.

---

# Rule 3 — Learn From First Principles

Whenever possible, start with the fundamental idea before learning tools or frameworks.

For example:

- Learn how browsers work before learning React.
- Learn JavaScript before learning React Hooks.
- Learn HTTP before learning API libraries.
- Learn CSS before learning Tailwind CSS.

Strong fundamentals make advanced topics much easier.

---

# Rule 4 — Official Documentation Is the Primary Source

Whenever the handbook refers you to official documentation, treat it as the primary learning resource.

Articles, blogs, videos, and tutorials are valuable supplements, but they should not replace official documentation.

Learning to read documentation is an essential engineering skill.

---

# Rule 5 — Never Copy Code You Don't Understand

If you paste code from a tutorial, Stack Overflow, GitHub, or an AI assistant, make sure you understand:

- What each part does.
- Why it is needed.
- What would happen if you removed or changed it.

Using code without understanding it creates technical debt in your own knowledge.

---

# Rule 6 — Experiment Actively

Reading is only the beginning.

Real understanding comes from experimentation.

Whenever possible:

- Remove code.
- Change values.
- Introduce mistakes.
- Observe behaviour.
- Compare results.

Breaking things in a controlled environment is one of the fastest ways to learn.

---

# Rule 7 — Build Mental Models

Do not try to memorize isolated facts.

Instead, build mental models.

A mental model explains how a system works as a whole.

When you understand the system, individual APIs become much easier to remember.

---

# Rule 8 — Think Like an Engineer

Whenever you solve a problem, ask yourself:

- Is this the simplest solution?
- Is it maintainable?
- Will another developer understand it?
- What trade-offs am I making?
- How will this scale?

Engineering is about making thoughtful decisions, not simply making code work.

---

# Rule 9 — There Is Rarely One Perfect Solution

Most engineering decisions involve trade-offs.

Instead of searching for the "best" solution, learn to compare options based on:

- Simplicity
- Performance
- Readability
- Scalability
- Maintainability
- User experience
- Team requirements

Learning to evaluate trade-offs is a key engineering skill.

---

# Rule 10 — Connect Every Topic

Knowledge should never exist in isolation.

As you learn something new, ask:

- How does this relate to previous chapters?
- Where will I use this later?
- How does this appear in production applications?
- How does this improve my current projects?

The strongest engineers connect ideas across different areas of software engineering.

---

# Rule 11 — Read Production Code

Writing code is only one part of engineering.

Reading existing code is equally important.

Whenever possible:

- Study real projects.
- Observe naming conventions.
- Follow data flow.
- Understand architecture.
- Identify design decisions.

The ability to understand unfamiliar code is a professional skill.

---

# Rule 12 — Keep an Engineering Journal

Every chapter should end with reflection.

Record:

- What you learned.
- What surprised you.
- What confused you.
- Questions you still have.
- Ideas worth revisiting.

Reflection strengthens long-term understanding.

---

# Rule 13 — Finish Assignments Honestly

Assignments are not tests.

They are opportunities to strengthen understanding.

If an assignment reveals a weakness, that is valuable information—not failure.

Take time to improve rather than rushing to completion.

---

# Rule 14 — Review Regularly

Learning is not complete after reading once.

Review previous material regularly.

Short, consistent revision sessions are far more effective than cramming.

---

# Rule 15 — Ask Questions Without Hesitation

Questions are a sign of curiosity, not weakness.

If something feels unclear, ask immediately.

Small misunderstandings often become much larger problems later.

Resolving confusion early builds stronger foundations.

---

# Rule 16 — AI Is a Mentor, Not a Replacement

Throughout this residency, AI will help explain concepts, review code, suggest improvements, and answer questions.

However, avoid asking AI to solve every problem immediately.

Think first.

Attempt a solution.

Then compare your reasoning with AI's suggestions.

The goal is to improve your engineering ability, not reduce your thinking.

---

# Rule 17 — Learn With Patience

Not every concept should be mastered in one sitting.

Some topics require:

- Reading
- Experimentation
- Practice
- Reflection
- Repetition

Learning deeply is more valuable than learning quickly.

---

# Rule 18 — Measure Progress by Understanding

Do not measure progress by:

- Number of chapters completed
- Hours studied
- Technologies covered

Instead, ask yourself:

- Can I explain this clearly?
- Can I teach it to someone else?
- Can I apply it in a new situation?
- Can I recognize it in production code?

Understanding is the true measure of progress.

---

# Rule 19 — Keep the Repository Organized

Treat this repository like a professional engineering project.

Every document should have a clear purpose.

Every file should belong in the correct folder.

An organized repository reflects organized thinking.

---

# Rule 20 — Think Beyond Today's Technology

Frameworks will change.

Languages will evolve.

Tools will improve.

Engineering principles remain valuable across technologies.

Focus on understanding ideas that will still matter years from now.

---

# Rule 21 — Enjoy the Process

Engineering is a lifelong journey.

There will always be more to learn.

Celebrate curiosity.

Embrace challenges.

Be patient with yourself.

Every chapter completed brings you one step closer to becoming the engineer you aspire to be.

---

# Final Reminder

Whenever you feel overwhelmed, return to these three principles:

1. Understand before memorizing.
2. Think before coding.
3. Build strong foundations.

Everything else in this residency is built upon these ideas.
