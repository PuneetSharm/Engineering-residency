# Folder Structure

> **"A well-organized repository reflects well-organized thinking."**

---

# Why This Structure Exists

This repository is more than a collection of notes.

It is designed to be:

- an engineering handbook,
- a learning journal,
- a project workspace,
- a portfolio,
- and a long-term knowledge base.

Each folder has a specific responsibility.

Keeping content in the correct place makes the repository easier to navigate, maintain, and expand over time.

---

# 00-Getting-Started

Purpose:

Introduce the residency.

Contents include:

- How to use the handbook
- Learning rules
- Mentorship charter
- Folder structure
- Roadmap

Read these files before starting the handbook.

---

# 01-Engineering-Handbook

Purpose:

The main textbook of the residency.

This contains all lessons, explanations, theory, engineering concepts, documentation walkthroughs, experiments, interview preparation, and learning material.

Do not write personal notes here.

Treat this folder as the official curriculum.

---

# 02-Journal

Purpose:

Your personal learning diary.

Use this folder to record:

- daily reflections,
- concepts you found difficult,
- questions,
- mistakes,
- insights,
- and progress.

This is your own writing.

---

# 03-Assignments

Purpose:

Hands-on work.

Every chapter that includes practical exercises should have its work stored here.

Examples:

- coding exercises,
- mini-projects,
- implementation tasks,
- research activities.

Keep assignment solutions separate from the handbook.

---

# 04-Developer-OS

Purpose:

The primary long-term engineering project.

Throughout the residency, this application will grow as you learn new concepts.

It will become a practical demonstration of your engineering skills.

---

# 05-Portfolio

Purpose:

Your public portfolio.

As you complete projects and gain experience, this folder will contain the source code for the portfolio website that showcases your work.

Unlike Developer OS, this project focuses on presentation and communication.

---

# 06-Revision

Purpose:

Concise summaries for quick review.

Examples:

- cheat sheets,
- mind maps,
- flash notes,
- interview summaries,
- key concepts.

These notes should be short and focused.

---

# 07-Office-Observations

Purpose:

Bridge learning with real-world experience.

Whenever you notice an interesting pattern in your workplace or a production codebase, document it here.

Examples:

- authentication flows,
- folder structures,
- API handling,
- state management,
- performance techniques,
- architecture decisions.

These observations help connect theory with practice.

---

# 08-Code-Snippets

Purpose:

A curated library of reusable code.

Only store code that you fully understand.

Examples:

- custom hooks,
- utility functions,
- reusable components,
- helper methods,
- common patterns.

Each snippet should include a brief explanation of when and why it should be used.

---

# 09-Diagrams

Purpose:

Visual understanding.

Store architecture diagrams, flowcharts, sequence diagrams, component relationships, and other visual aids that help explain systems.

Understanding improves when concepts are visualized.

---

# 10-Resources

Purpose:

Reference material.

This folder can include:

- useful links,
- recommended books,
- documentation references,
- articles,
- videos,
- research papers,
- learning resources.

Think of this as your engineering library.

---

# General Guidelines

## Keep Responsibilities Clear

Each folder has a single purpose.

Avoid mixing different types of content.

For example:

- reflections belong in Journal,
- lesson content belongs in Engineering Handbook,
- implementation belongs in Developer OS,
- revision notes belong in Revision.

---

## Name Files Clearly

Use descriptive names.

Prefer:

- `Authentication.md`
- `React-Reconciliation.md`
- `JWT-Refresh-Flow.md`

Avoid names like:

- `Notes1.md`
- `Test.md`
- `NewFile.md`

---

## Keep Everything Version Controlled

Commit your work regularly.

Small commits with meaningful messages make it easier to review your progress and revisit earlier decisions.

---

# Final Principle

Every file in this repository should answer one question:

**"Does this belong here?"**

If the answer is unclear, reconsider where it should be placed.

A clean repository supports clear thinking, easier maintenance, and better engineering habits.
