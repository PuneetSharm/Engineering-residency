# The Difference Between Programming and Engineering

Many beginners use these words as if they mean the same thing.

They do not.

Programming is the act of writing instructions that a computer can execute.

Engineering is the discipline of designing, building, testing, improving, and maintaining systems that solve real problems under real constraints.

Programming answers:

> "How do I write this?"

Engineering answers:

> "Should this exist?"

> "Is this the right approach?"

> "What happens when ten million people use it?"

> "Can another engineer understand this six months from now?"

> "What trade-offs am I making?"

Programming is an important engineering skill.

It is not engineering itself.

# Mental Models

One of the biggest differences between beginners and experienced engineers is not intelligence.

It is not memory.

It is not even years of experience.

It is something much simpler and much more powerful.

Experienced engineers build **mental models**.

If you understand what a mental model is and learn how to build one, every technology you learn from today onwards will become easier.

Before defining the term, let us understand it through an everyday example.

---

# Imagine You Have Never Driven a Car

Suppose someone asks you to drive a manual car.

You have never driven one before.

So you watch a five-minute YouTube video.

The instructor says:

1. Press the clutch.
2. Shift to first gear.
3. Slowly release the clutch.
4. Press the accelerator.

You memorise all four steps.

Now imagine sitting inside an actual car.

You follow the exact sequence.

The car stalls.

You try again.

It stalls again.

Why?

Because you memorised instructions.

You never understood **what the clutch is actually doing.**

---

Now imagine another learner.

Instead of memorising the sequence, they first learn:

- The engine is always rotating.
- The wheels are initially stationary.
- The clutch temporarily disconnects the engine from the wheels.
- Releasing the clutch gradually transfers power from the engine to the wheels.

Suddenly, the four instructions make sense.

If the car is on a slope...

If the engine speed changes...

If another car has a different clutch...

They can still adapt.

Why?

Because they understand the system.

This understanding is their mental model.

---

# So What Is a Mental Model?

A mental model is your internal explanation of how something works.

It is not a definition copied from documentation.

It is not something memorised for an interview.

It is the picture your brain creates that explains:

- what exists,
- why it exists,
- how the parts interact,
- and what happens when one part changes.

When your mental model is strong, you no longer depend on memorising steps.

You begin reasoning.

---

# Why Mental Models Matter in Software Engineering

Let's imagine another situation.

A senior engineer joins a new company.

The project uses a frontend framework they have never seen before.

Surprisingly, within a week, they become productive.

A beginner might think:

> "They must have learned this framework before."

In many cases, they haven't.

So how are they learning so quickly?

Because they are not learning from zero.

They already understand:

- Components
- State
- Rendering
- User interactions
- Data flow
- APIs
- Browser behaviour

The new framework simply uses different syntax to solve familiar problems.

Their existing mental models allow them to map new concepts onto knowledge they already possess.

---

# Building Your First Engineering Mental Model

Throughout this residency, every time we learn something new, we will build its mental model before learning its syntax.

For every topic, we will answer these questions:

## 1. What problem existed?

Every technology is created to solve a problem.

If you don't understand the problem, the solution will feel random.

## 2. Why wasn't the previous solution good enough?

Most technologies are improvements over earlier approaches.

## 3. How does the new solution work?

Only now do we study the technology itself.

Not before.

---

## 4. What are its limitations?

No technology is perfect.

Every engineering decision involves trade-offs.

Understanding limitations is just as important as understanding advantages.

Knowledge becomes meaningful only when connected to real-world applications.

# Example: HTML Input

Imagine someone asks:

> Why does an `<input>` element have a `name` attribute?

Many beginners answer:

> Because Formik needs it.

This is not wrong.

But it is incomplete.

A stronger mental model looks like this.

Long before React existed, browsers already supported HTML forms.

When a user submits a form, the browser collects all the input values.

But how does it know which value belongs to which field?

It needs an identifier.

That identifier is the `name` attribute.

When the browser sends form data, it creates key-value pairs.

For example:

```text
firstName=Puneet
email=puneet@example.com
```

The browser uses the `name` attribute as the key.

Libraries like Formik and React Hook Form simply build upon this existing browser behaviour.

They did not invent it.

Notice what happened.

Instead of memorising:

> "`name` is required."

you now understand:

> "Browsers need a way to identify submitted data."

That understanding will remain useful regardless of which framework you use in the future.

# Thinking Like an Engineer

From today onwards, every new technology should trigger the same questions in your mind.

Instead of asking:

> "How do I use this?"

Train yourself to ask:

- What problem does it solve?
- Why was it created?
- What existed before it?
- Why wasn't the previous solution sufficient?
- What trade-offs does this introduce?
- Would I choose this in every project?

If you repeatedly ask these questions, you will naturally start building strong mental models.

That is how experienced engineers learn quickly.

They do not memorise more.

They understand more.

"I know React."

"I know Next.js."

"I know Redux."

"I know Docker."

"I know Kubernetes."

Experienced engineers measure progress differently.

They ask:

Because if you understand **why**, learning **how** becomes much easier.

Never chase technologies.

Technologies will continue changing throughout your career.

Strong mental models will continue helping you understand them.

# The Biggest Difference Between You and a Senior Engineer

This section may surprise you.

A senior engineer is **not** simply someone who knows more React.

A senior engineer is **not** someone who remembers more APIs.

A senior engineer is **not** someone who types faster.

Those things help, but they are not the primary difference.

The biggest difference is that they have developed a reliable way of thinking.

When they receive a task, their brain automatically begins asking questions.

Most beginners don't.

---

# Imagine Your Manager Gives You a Task

Your manager says:

> "We need to add file download functionality."

Pause for a moment.

Do not think about code.

Instead, ask yourself:

**What would you think first?**

Many developers immediately search:

> "React file download"

or

> "Blob download example"

That works.

But it skips the most important part.

Understanding the problem.

---

# What a Beginner Often Thinks

A beginner's internal conversation usually looks like this:

- Which package should I install?
- Is there a library?
- Can AI generate this?
- Which tutorial should I watch?

Notice that every question is about the solution.

None of the questions are about the problem.

---

# What an Experienced Engineer Thinks

Now imagine an experienced engineer receiving the same task.

Their internal conversation is very different.

They begin asking questions like these:

- What exactly are we downloading?
- Where does the file come from?
- Which API returns it?
- What format is it?
- Is authentication required?
- How large can the file become?
- Should it open in the browser or download directly?
- Should we show progress?
- What happens if the download fails?
- Do we need retry behaviour?
- Should we log failures?
- Does this work on mobile browsers?
- Does the backend already send the correct headers?

Notice something remarkable.

They still haven't written a single line of code.

Yet they are already solving the problem.

---

# Engineering Starts Before Coding

One of the biggest misconceptions in software development is that engineering begins when VS Code is opened.

It doesn't.

Engineering begins when you start asking good questions.

Code is simply the final step.

This explains why experienced engineers often write code faster.

It is not because they type faster.

It is because most of the thinking has already been done.

---

# The Engineering Thinking Framework

Throughout this residency, every feature we build will follow the same thinking process.

Whenever you receive a requirement, ask these questions in order.

## Step 1 — Understand the Requirement

What exactly is being requested?

Can you explain the requirement in your own words?

If you cannot explain it, you probably do not understand it yet.

---

## Step 2 — Identify the Problem

Why does this feature exist?

What user problem is it solving?

What business problem is it solving?

---

## Step 3 — Gather Information

Before writing code, determine:

- available APIs,
- data structure,
- design files,
- validations,
- security requirements,
- performance expectations,
- browser compatibility.

---

## Step 4 — Plan

Only now should you begin thinking about implementation.

Examples:

- folder structure,
- reusable components,
- state management,
- API integration,
- testing strategy.

---

## Step 5 — Implement

Now you write code.

Notice how implementation is only the fifth step.

---

## Step 6 — Verify

Does it actually solve the original problem?

Not:

> "Does it compile?"

Instead ask:

> "Does it solve the user's problem correctly?"

---

# Why AI Sometimes Becomes a Trap

AI is incredibly powerful.

But it has one weakness.

It usually answers the question you ask.

If you ask:

> "Generate a React file download."

AI will happily generate one.

But if you never asked:

- Which file?
- Which headers?
- Which authentication?
- Which browser?
- Which error cases?

Then the generated code may solve only part of the real problem.

AI is most valuable after you understand the problem.

Not before.
